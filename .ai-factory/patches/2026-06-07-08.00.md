# Telegram SDK initialization broken in browser dev mode

**Date:** 2026-06-07 08:00
**Files:** web/src/main.tsx, web/vite.config.ts, web/src/components/Chat.tsx
**Severity:** high

## Problem

Приложение не работало при локальной разработке:
- В браузере API-запросы падали с 401 (нет initData)
- Vite dev-сервер не проксировал `/api` запросы к Go-бекенду
- После исчерпания дневного лимита поле ввода чата оставалось видимым

## Root Cause

1. **`isTMA()` не awaited** — в `@telegram-apps/sdk` v3 `isTMA()` асинхронная и возвращает `Promise<boolean>`. Вызов без `await` всегда truthy (Promise — объект), поэтому блок `else` с `mockTelegramEnv()` никогда не выполнялся. `init()` вызывался без mock-окружения → `initData.raw()` всегда возвращал `undefined`.

2. **Пропущен `initData.restore()`** — после `init()` необходимо вызвать `initData.restore()`, иначе методы `initData.user()`, `initData.raw()` возвращают `null`/`undefined`.

3. **Нет Vite proxy** — `vite.config.ts` не содержал `server.proxy`, поэтому при `pnpm dev` запросы к `/api/*` шли на порт Vite (5173) вместо Go-сервера (8080).

4. **Ошибка 429 не обрабатывалась** — при превышении дневного лимита бекенд возвращал 429 с полями `daily_used`, `daily_limit`, `is_premium`, но фронтенд не обновлял состояние usage из ответа.

## Solution

1. **main.tsx:** Обёрнута инициализация SDK в async-функцию, `isTMA()` вызывается с `await`. После `init()` добавлен `initData.restore()`. Рендер React-дерева перенесён в `.then()`.
2. **vite.config.ts:** Добавлен `server.proxy` для `/api` → `http://localhost:8080`.
3. **Chat.tsx:** В catch-блоке добавлена проверка `err instanceof ApiError && err.status === 429` — если это 429, из `err.data` извлекаются `daily_used`, `daily_limit`, `is_premium` и обновляется состояние `usage`.

## Prevention

- Все SDK-функции, возвращающие Promise (`isTMA()` и др.), должны вызываться с `await`
- После `init()` из `@telegram-apps/sdk` всегда вызывать `initData.restore()`
- Для Vite dev-сервера всегда настраивать proxy при наличии отдельного API-сервера
- Ошибки API (особенно 429) должны обновлять соответствующее состояние на фронтенде
